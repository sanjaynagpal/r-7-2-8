Internal explainer — appdev → svc_appdev migration

SSH trust mesh

The application is moving from four old servers to four new ones, and the account it runs as is changing name. This is how we make that invisible to every script that connects between them, using Ansible — explained assuming you've never used Ansible before.

1 — the problem

One script, two account names

Today the application runs as appdev on four RHEL7 servers. It's moving to four new RHEL8 servers, where — for tighter permissions — it will run as a different account, svc_appdev. During the migration both sets of servers are live at once, and the application's own scripts SSH between them: a batch job on one box reaches over to stage a file or kick off work on another.

Those scripts just say things like ssh rhel8-app01 ./collect.sh. They don't know or care which account they're running as — they assume it's whatever it always was. The moment the remote account's name changes, that assumption breaks, and fixing it by teaching every script about two possible usernames would mean editing application code we'd rather not touch at all.

2 — what ansible actually is

A tool that runs the same steps on many machines over SSH

Ansible isn't installed on the servers it manages. From one controller — your laptop, or a jump box — it connects out over ordinary SSH and runs a set of instructions, called a playbook, against as many hosts as you point it at. Run it again and it only changes what's actually different from what you asked for; a host that's already correct is left alone. That's what "idempotent" means below.

playbook
a file listing the steps to run, in order — the thing you hand to Ansible
role / task
a task is one step ("create this user"); a role bundles related tasks together and can be reused
module
the actual code behind a task, e.g. "create a user" or "edit this block of a file" — needs Python on the target
raw
a fallback that runs a plain shell command instead of a module — no Python required
idempotent
running it twice gives the same end state; the second run changes nothing if the first one already succeeded

3 — the trick

Let SSH rewrite the username, not the script

SSH has its own address book: ~/.ssh/config. It lets an account say "whenever I connect to this alias, actually log in as this user." This project generates and maintains that address book automatically, for every account, listing every host in the mesh — so a script that just says ssh rhel8-app01 keeps working no matter which platform runs it or which platform it's reaching.

Why it has to be at the top of the file: SSH uses the first matching entry it finds for a given host. This project inserts its block at the very top of ~/.ssh/config, so nothing an admin later appends below it — a stray Host * line, for instance — can silently override the mapping.

4 — why it's not just one connection

Every host has to trust several others, in both directions

It's not one script SSHing one other box. Any of the four new servers may need to reach any of the other new servers, and, while both platforms are live, any of the four old servers too — and vice versa. The old servers' existing trust with each other is left exactly as it is; this project only adds the paths that cross the platform boundary, plus the RHEL8-to-RHEL8 paths RHEL8 needs among itself.

5 — how it's actually built

Two passes: collect everyone's keys, then write everyone's files

To build those address books, Ansible first has to know every account's public key and every server's host key. So the run has two phases. The first visits every host and reads what's already there. The second uses what it just read to write the same three files — authorized_keys, known_hosts, and ~/.ssh/config — onto every host, so they all agree.

The two platforms are read and written differently, because RHEL7 is being retired: nothing new gets installed there, and the servers can't even run Ansible's normal toolkit (it needs Python 3, which this old RHEL7 setup doesn't offer to a current Ansible). So RHEL7 is handled with a small bash script sent over as plain text; RHEL8 gets Ansible's usual, fully managed approach. Both sides render the exact same template, so the files always agree in content even though they're written by different means.

6 — guardrails

What keeps this safe to rerun

Marked blocks only
Every edit sits between its own BEGIN/END markers. Nothing outside that block is ever touched or reformatted.
Keys are never replaced
A key is generated only if an account has none at all. An existing key, however old, is reused as-is.
Host identity is verified
Real host keys are collected and checked on every connection — no "trust the first time you see it" shortcut, anywhere.
Keys are source-locked
Each authorized key is restricted to the IP address of the host it belongs to, so a copied key is useless from anywhere else.
All or nothing
If even one host in the mesh can't be reached, the run stops before writing anything — never a half-updated set of trust files.
Turning it off is one setting
Once the app has fully moved, flipping rhel7_in_mesh: false re-renders RHEL8's files without RHEL7 — even if those old servers are already off.
